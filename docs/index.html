01 / OVERVIEW

專案目標與成果

將指定漁業調查表的手寫 PDF、掃描影像及 DOCX 轉為標準資料，經人員確認後保存、查詢與匯出。第一階段成功標準是「完整辨識、可修正、可持久保存」，再擴充管理與分析。

4 類母版沿海網具、釣具、延繩釣、生物量測
2 條 AI 路徑Gemini / OpenAI，共用資料結構
人工覆核不確定值保留、修正後入庫

使用角色：資料提供者負責原始表單；覆核人員確認日期、魚種與數值；資料管理者管理分類與匯出；開發維運人員負責部署、測試及復原。

04 / WORKFLOW

目標架構與作業流程

上傳與分類→逐頁／分區解析→正規化與驗證→人工覆核→Supabase→查詢／CSV

Streamlit 提供操作入口；Python 解析器處理供應商差異；Pydantic 驗證資料；資料庫層以交易保存主檔與明細。SQLite 用於明確的本機開發，staging 與正式資料必須使用 PostgreSQL。

建議流程狀態

uploaded → parsed → needs_review → approved → saved；解析或入庫失敗進入 failed。必須區分「結構有效」「內容正確」「保存成功」；部分頁失敗須標示，不可呈現全批完成。完整狀態追蹤仍屬後續實作。

錯誤處理原則

暫時 API 錯誤採有限重試；額度不足提示處理帳務；資料驗證失敗保留待修正資料；空結果不視為成功。資料庫失敗停止寫入並回滾，不改寫到另一個後端。

05 / DATA CONTRACT

資料標準與 schema 管理

領域核心資料規劃目標表
匯入來源批次、檔名、頁數、來源識別、模型執行紀錄import_batches / source_documents / ai_extraction_runs
漁撈作業船名、日期、漁法、時間、背景條件fishery_operations / operation_locations
漁獲原始魚種、標準魚種、尾數、公斤重量catch_records
生物學採樣背景、個體編號、尾叉長、全長、克重量bio_sample_batches / biological_measurements
主檔與規格分類、母版、船、港、魚種、欄位定義database_categories / form_templates / vessels / ports / species_catalog / field_definitions

資料品質規則（目標）

  • 缺值與 0 分開；不可用 0 或空 placeholder 代替未辨識資料。
  • 保留原始日期與曆法證據，民國轉西元須明確；檔名僅輔助，衝突交人員確認。
  • 漁獲重量用 kg，個體重量用 g；尾叉長與全長均以 mm 儲存但不得混用。
  • 保留原始魚名與標準化名稱；無法確定分類時不強制猜測。
  • 頁碼、表格區域、原始列號保留作為追溯欄位；跨頁合併不能只依日期。
  • 所有轉換規則標示版本；人工覆核後不得被重新解析無提示覆寫。

已知相容落差

現行 CRUD 仍依賴 fishery_logs、整數 ID、name、legacy_log_id；目標 SQL 使用 UUID、category_name_zh 與新外鍵。欄位字典中的 code 映射亦與 SQL 的 UUID FK 有差異。目標 SQL 不能直接當作既有庫的 migration。

先盤點 staging 的 table、column、PK、FK、NOT NULL、索引及既有資料，再決定最小相容方案。P0-A 僅處理完成持久化所必需的差異；全面資料標準整併歸 P1。

06 / WORK PACKAGES

依優先順序執行

P0-A｜Supabase staging persistence 進行中，未驗收
  1. 確認 Git 狀態、版本、staging 目標與登入狀態。
  2. 唯讀盤點 PostgreSQL schema，與實際 CRUD 比對。
  3. 設計必要相容修正及資料保留／回復方案，先測試再執行 migration。
  4. Secrets 設定連線與 DFIS_REQUIRE_POSTGRES=true；不得將機密寫入 Git。
  5. 測試完成版本部署到 staging，確認實際後端為 PostgreSQL。
  6. 由 Cloud 寫入唯一 marker，實際重啟 App，再查詢及匯出比對。

交付：schema 差異表、最小修正、完整測試、重啟證據與 CSV 校驗。無證據不結案。

P0-B｜生物學表格完整辨識 後續

建立 BIO_MESH_001 人工真值；表頭、左表、右表分區解析；依頁碼與編號合併；處理同魚種向下沿用，但不得越過明確分組界線。空白列不虛構個體，有量測值的列不得丟棄。

交付：專用解析器、來源定位、缺列報告、數值正確率與人工覆核案例。先以固定測試集驗證，再擴充其他樣本。

P1｜雙模型驗證與資料契約對齊 後續

Gemini／OpenAI 使用同樣原件、真值與評分規則，比較完整率、欄位正確率、耗時、重試與成本。統一 Pydantic、欄位字典、SQL 與 CRUD 的主鍵、必填、單位及刪除策略。

交付：雙模型矩陣、欄位映射、相容測試、固定樣本端到端報告。

P2｜維運與擴充 待後續排程

在前項驗收後，評估模組化、來源檔保存、Auth、RLS、Storage、稽核及背景任務。各項分別定義需求、資料權限、成本與驗收，不以本頁規劃視為已實作。

07 / ACCEPTANCE

測試與驗收門檻

類別完成門檻必留證據
P0-A 持久化Cloud 寫入後實際 reboot；新 session 查到相同資料；CSV 一致；無 fallbackcommit、marker、ID、重啟前後時間、後端確認、匯出比對
多頁完整性每頁均有成功／空白／失敗狀態；有效列不漏、不重複逐頁清單與人工真值對照
生物學數值固定集數值正確率先達 90%，後續 95%；欄位錯置為 0；有效列完整正確儲存格數／應辨識數值格數；缺值列為錯誤
人工覆核修改值經入庫、查詢、匯出保持一致；未知值清楚標記覆核前後樣本與持久化比對
交易安全中途失敗無半筆主檔／明細；重試不造成未提示重複真實 staging 故障與回滾測試
雙模型各完成漁撈與生物表解析、覆核、入庫及查詢相同案例、模型識別、參數及結果

OCR 計分排除已人工標為不可辨識的格，但須另列其數量；測試集固定後不可只挑成功頁。30 項歷史單元測試與資料庫 mock 不替代上述驗收。

08 / DELIVERY

部署、資料保留與維運

版本流程：本機修改 → 測試 → 功能分支 → staging → 驗收證據 → 審查合併 → 正式發布。記錄 commit 與部署時間；本頁 GitHub Pages 僅供閱讀，不執行 Python、AI 或資料庫操作。

  • Local 使用隔離測試資料；staging 與 production 的目標必須明確區分。
  • 連線、API 金鑰僅放受控 Secrets／環境；日誌不輸出完整憑證或原始敏感錯誤。
  • 變更 schema 前保存可還原備份；先在 staging 測試升級及復原，記錄筆數與關聯一致性。
  • 程式回退不等於 schema 回退；每次發版須確認上一版是否可讀寫新版 schema。
  • 正式資料進入前明確界定使用者範圍及可用存取限制；Auth/RLS 實作仍依 P2 排程。
  • 長期留存原件、刪除政策與備份保存期由專案負責人核定；本階段不假設 Storage 已完成。

維運指標規劃：解析成功率、缺頁／缺列數、人工修正比例、DB 錯誤率、單件耗時與 API 費用。價格與模型選擇於實測時重新核對，本計畫不預設固定費率。

09 / MANAGEMENT

時程、責任與優化管理

沿用 implementation_plan.md 的四週工作節奏，從前置條件齊備後起算；這是估算，不是已排定日期。登入、schema 差異或驗收不通過時，後續里程碑順延。

階段重點負責與出口
第 1 週P0-A、固定樣本準備維運／開發：持久化證據；領域人員：真值
第 2 週P0-B 分區逐列解析開發／覆核：完整率與正確率
第 3 週P1 雙模型及資料對齊開發／資料管理：跨模型閉環
第 4 週試運行與交付整理專案負責人：驗收、限制、下一期清單

每項細部優化的登錄格式

需求 ID、使用情境、重現樣本、預期行為、所屬 P0/P1/P2、相依工作、影響檔案／schema、驗收標準、責任人、估算、結果證據與回復方案。依據為實際錯誤及使用需求，避免每次測試只留下截圖而無可重現案例。

資源與費用

需投入領域覆核、Python 開發、部署維運與驗收人力。預算分為 API 用量、雲端主機／資料庫、檔案保留及人工覆核工時；先量測每件頁數、重試次數與費用，再核定月上限。P2 擴充須另估。

主要風險

schema 混用造成寫入失敗；AI 漏列或年份誤判；測試資料污染正式資料；未提交版本與 Cloud 不一致；憑證失效或 API 額度不足。依序用 schema 盤點、固定真值、環境隔離、commit 證據及可讀錯誤降低風險。
